Rows that meet should already share a slice

Lesson 1. The cost of a Redshift join is usually the copy that happens before the comparison.

A compute node is split into slices. Each slice owns its own rows and does its own work. A join compares a row from one table with a row from another. If those two rows live on different slices, Redshift copies data across the network first. That copy is called redistribution, or a broadcast when a whole table is sent everywhere.

Distribution is the rule that picks the slice:

  • DISTKEY(col) — rows with the same value of col land on the same slice.
  • DISTSTYLE EVEN — rows are spread with no regard to values. Equal values do not meet.
  • DISTSTYLE ALL — a full copy sits on every node, so nothing has to be fetched at query time.
  • DISTSTYLE AUTO — Redshift chooses, and it can change. Read diststyle from SVV_TABLE_INFO before you trust a guess.

The move

Join on the distribution key of the large table. If the other side uses the same key, the matching rows are already together and the plan says DS_DIST_NONE. If the other side is ALL, the plan says DS_DIST_ALL_NONE: still no copy at query time, because the copy happened when the table was loaded.

Join on anything else and the planner has to move rows. A small side may be broadcast (DS_BCAST_INNER). One or both large sides get redistributed (DS_DIST_INNER, DS_DIST_BOTH). The SQL result is the same. The cluster did extra work to make the rows meet.

EXPLAIN
SELECT o.order_id, c.email
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id;

Look at the join line, not the scan. DS_DIST_NONE or DS_DIST_ALL_NONE means this query respected the tables. Any other DS_ label means rows moved. If orders and customers are both DISTKEY(customer_id), the join above should not move them. The same tables joined on o.email = c.email should.

Before the drill: orders is DISTKEY(customer_id), customers is DISTSTYLE ALL. You join on customer_id. Do any rows move when the query runs?
